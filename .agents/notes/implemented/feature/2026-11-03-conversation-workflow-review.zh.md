# Agent Note: 会话内工作流审核

Status: implemented

[English](2026-11-03-conversation-workflow-review.md) | 中文

## 问题

用户从对话启动工作流后，必须到工作流页面查找对应实例，才能审核输出。当其他入口已经处理任务时，继续使用已打开的详情也可能将本次审核与下一项审核混淆。

## 决策

业务工作流插件在输入框上方注册 Session 作用域的卡片，并打开 DH 内的审核对话框。卡片按部署租户、本机办理人和准确的发起 Session 查询 Flowable 原生人工任务，不依赖当前工作流绑定或最近实例窗口。卡片显示最早的 30 项任务和总数。它按实例身份归组任务及跟进状态：流程名称、状态和实例编号组成上层标题，缩进的当前步骤携带各自的审核按钮。任务名称仅出现一次。未被主动跟进的实例先以实例身份显示，读取详情后显示名称。选择任务不会通过审核。

经过认证的会话 API 在读取审核依据或提交决定前，检查本机会话准入和准确的实例归属。详情展示已保存人工节点选取的输入及上游结果。对话框保留准确的任务编号；该任务结束后，不会悄然通过下一项任务。现有工作台与会话 API 共用同一审核操作，并在同一 Host 内拒绝同一实例的重叠审核请求。通过会完成原生人工任务；退回保留原有的终止实例行为。agent（智能体）工具不增加审核操作。

注册负责轮询及串行的读取和决定提交。Session 释放时停止轮询，并等待已接受的决定提交结束。选择变更后忽略旧详情响应。引擎故障时返回部署的轮询间隔以支持恢复；两个入口均读取引擎，不维护独立审核记录。卡片是实时操作界面，不是模型消息或伪造的对话事件。

## 考虑过的替代方案

**只保留工作流页面。** 这仍然要求中断对话并查找实例，无法解决本次改动的问题。

**让 agent 解释同意消息。** 这会将人工决定的权限交给模型，并使目标任务不明确。显式界面操作携带准确的任务身份。

**另建聊天审核记录。** 第二份记录可能与现有引擎任务不一致，因此两个入口共用同一 Flowable 任务和办理操作。

## 影响

实现保留在现有业务工作流包内。通过读取引擎，切回普通聊天、刷新页面和重连后仍能恢复卡片。本机操作人认证仍是唯一审核身份；企业审核人分配和退回修改分支留待后续实现。最早任务窗口限制单次响应，同时保留完整待审数量。此 Host 的重叠请求保护不提供分布式审核事务。

控制器测试覆盖合并读取、重复点击、详情替换、任务结束、故障恢复，以及排队决定提交期间的释放。构建后的企业微信与 Flowable 场景覆盖会话卡片、准确内容、刷新、切回普通聊天、跨 Session 拒绝、通过、过期重提，以及外部退回在已打开详情中的同步。归属本包的 aria 快照固定卡片和详情展示。
