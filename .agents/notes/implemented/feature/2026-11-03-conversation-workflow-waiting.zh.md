# Agent Note: 在发起会话中等待业务工作流审核

Status: implemented

[English](2026-11-03-conversation-workflow-waiting.md) | 中文

## 问题

启动工具立即返回实例编号，使发起 agent（智能体）的轮次在人工审核前结束。通过后引擎会继续，但会话不会自动获得结果。仅有审核卡片不能保留仍待完成的用户请求。

## 决策

业务工作流启动后，将已接受的实例关联到发起 Session。成功启动的工具结果通过原生 `concludesTurn` 标记停止后续模型步骤。包内监听器通过现有 `agent/turn-stopping` 扩展，在 Flowable 执行或等待时保持该 agent 的轮次打开。它按配置间隔读取引擎事实，挂起时不产生模型请求。通过后继续原生引擎执行，包括受限的 DH 分析节点。完成、终止或节点受阻时，将已记录的插件通知作为引导输入送入同一个 agent，使其无需新用户消息即可反馈已保存结果。

跟进归属保存在独立的 `business_workflow_follows` 版本 1 存储域，仅存储实例、Session 及租户身份。引擎仍是执行与审核的权威来源。重新打开已关联的本机 Session 时，唤醒空闲 agent 并继续跟进已有实例。显式界面关联支持旧实例。用户输入排队时释放停止边界，使其能够被处理；非释放原因的取消会解除跟进，但不取消实例。释放时保留归属、终止轮询、等待回调结束并关闭存储。

删除跟进记录前，先将结果通知刷新到 Session 日志。必要时先省略输出，再省略可选详情，使完整模型可见消息小于 64 KiB。在刷新与删除之间崩溃可能重复通知；不承诺跨存储严格一次投递。通知标明插件来源，并在对话记录中折叠。通知携带参考数据，不授权通过审核或跳过节点。工具权限和人工决定校验保持不变。

现有会话卡片展示执行和等待阶段，并支持对旧实例或已停止跟进的会话显式恢复。原生停止控件只停止跟进；终止引擎实例仍须显式工作流操作。实现保留在业务工作流包内。

## 考虑过的替代方案

**保留独立的启动回执。** 审核和结果仍未完成时，用户请求却已呈现为结束。

**让启动工具一直等待人工决定。** 长期工具调用会将审核时长与工具期限、传输生命周期耦合。现有轮次停止扩展可在启动工具完成后挂起会话。

**让模型轮询进度。** 在确定性的等待期间反复请求模型会消耗 token。Host 读取引擎状态，只有出现新工作时才恢复模型。

**将工作流控制移入 agent loop（智能体循环）。** 现有扩展已经支持保持轮次打开及引导继续，修改核心循环不会增加所需行为。

## 影响

正常执行在人工审核期间保持同一发起轮次打开，之后自动反馈最终结果。Host 重启后旧进程已不存在，因此可能需要在同一 Session 中开启新轮次；跟进归属仍指向已接受实例。重新打开已保存跟进时，可能消耗一次确认请求。用户取消保留引擎实例，不确定的外部操作仍遵循现有引擎失败策略。

归属本包的测试覆盖挂起、有界投递、保存与重新打开、排队输入、用户取消、释放、故障、归属、终止及步骤受阻。构建后的浏览器场景验证通过前发起轮次仍打开、等待期间模型调用次数不变、刷新恢复，以及通过后同一会话自动反馈已保存结果。稳定的模型可见通知由本包快照固定。
